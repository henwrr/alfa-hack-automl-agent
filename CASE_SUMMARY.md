# AutoML-хакатон: разбор кейса и локальных материалов

Исследованы все 20 страниц PDF, включая визуальную проверку формул и приложений, `baseline.py`, `requirements.txt`, оба `task.md`, оба словаря и фактические CSV. Ниже отдельно отмечены требования организаторов и выводы из переданных локальных файлов. PDF — первичный источник правил; локальные файлы помогают понять данные и пример запуска, но в нескольких местах не совпадают с PDF. Пользовательский приоритет для последующей разработки: CLI и надёжный harness важнее максимального public score; численного порога метрик нет; срок готовности — до 26 октября; один запуск может занимать до 3 часов. Дополнительных требований организаторов пользователь не передал.

## 1. Требования, прямо заданные в PDF

### Цель и поведение решения

Нужно сдать универсального AI-агента, который читает описание новой ML-задачи, изучает структуру данных, определяет тип задачи и формат ответа, строит решение, проверяет гипотезы на собственной валидации и записывает предсказания. Ожидается работа как минимум с регрессией и классификацией; в постановке также сказано «и другие задачи машинного обучения», без их перечня. Одна и та же версия кода должна запускаться и на публичных, и на ранее неизвестных приватных задачах без ручной настройки на конкретный набор (стр. 5, 8, 16–17).

### Архив, запуск и результат

- На платформу передаётся ZIP. В корне архива должен лежать `solution.py`, единая точка входа. Вспомогательные модули допустимы внутри архива; `solution.py` должен импортировать их и запускать нужную логику (стр. 6).
- Платформа запускает решение в Docker. Переменные окружения, интерфейс запуска и формат результата, согласно PDF, зафиксированы в `baseline.py`; интерфейс требуется соблюдать строго (стр. 6).
- На каждую задачу агент запускается отдельно, получает только её материалы и формирует ответ для неё. Файлы и результаты между задачами не переносятся (стр. 17).
- Внутри запуска агент самостоятельно формирует валидацию только на обучающих данных, проводит эксперименты и рассчитывает их метрики. Платформа не оценивает промежуточные результаты на скрытом тесте и не возвращает такую обратную связь (стр. 17).
- Вывод должен соответствовать формату, зафиксированному в `baseline.py`; точные имена переменных, входных путей и способ передачи результата из PDF восстановить нельзя, потому что локальная копия baseline такого контракта не содержит (стр. 6–7; подробный разбор ниже).

### Публичная и приватная проверка

Публичный этап содержит две задачи: регрессию и многоклассовую классификацию. Платформа считает метрики по скрытым целям тестовых выборок, объединяет баллы в public score, показывает результат участникам; отправки ограничены дневным лимитом (стр. 16).

Для private-этапа есть две новые задачи с нераскрытыми содержанием и метриками. Платформа выбирает сохранённую версию решения с лучшим public score и запускает её через `solution.py` на приватных данных, передав описание и данные по тому же интерфейсу. Код решения должен оставаться неизменным; ограничения по времени, ресурсам и формату сохраняются (стр. 16–17). Детали приватных задач, их метрики и тестовые размеры в материалах отсутствуют.

### Метрики и итоговый балл

Для регрессии используется RMSE на исходной шкале таргета; здесь \(n\) — число тестовых объектов, \(y_i\) — истинное значение, \(\hat y_i\) — предсказание агента:

\[
\mathrm{RMSE}=\sqrt{\frac{1}{n}\sum_{i=1}^{n}(y_i-\hat y_i)^2}.
\]

Меньше — лучше. Для классификации используется Macro F1: сначала F1 считается отдельно по каждому из \(K\) классов, где \(TP_k\), \(FP_k\), \(FN_k\) — верные положительные, ложные положительные и ложные отрицательные предсказания класса \(k\), затем F1 усредняется с одинаковым весом:

\[
F1_k=\frac{2TP_k}{2TP_k+FP_k+FN_k},\qquad
\mathrm{MacroF1}=\frac{1}{K}\sum_{k=1}^{K}F1_k.
\]

Больше Macro F1 — лучше. Классификационная Accuracy и Weighted F1 в публичной задаче справочные и в итоговый public score не входят (стр. 10, 18).

Каждая метрика нормируется относительно метрики бейзлайна на той же тестовой выборке. Обозначим бейзлайновые значения как \(B_{RMSE}>0\) и \(B_{F1}<1\). Тогда:

\[
S_{reg}=100\cdot\max\left(0,1-\frac{RMSE}{B_{RMSE}}\right),\qquad
S_{cls}=100\cdot\max\left(0,\frac{MacroF1-B_{F1}}{1-B_{F1}}\right).
\]

Результат на уровне бейзлайна или хуже даёт 0 баллов, идеальная метрика — 100. Обе публичные задачи имеют одинаковый вес:

\[
Score_{public}=\frac{S_{reg}+S_{cls}}{2}.
\]

Для двух приватных задач действует аналогичное среднее их баллов:

\[
Score_{private}=\frac{S_1+S_2}{2}.
\]

Чем выше итоговый score в диапазоне 0–100, тем выше позиция в лидерборде (стр. 18–19). Значения метрик бейзлайна в PDF и локальных материалах не приведены, поэтому численно пересчитать score по этим данным нельзя. Пользователь отдельно подтвердил, что численного целевого порога качества не задаёт.

## 2. Что означают агентность и AutoResearch в этом кейсе

PDF противопоставляет ограниченный AutoML агентной системе. AutoML автоматически перебирает варианты внутри заранее заданного разработчиками сценария. Агент под управлением LLM удерживает контекст и историю результатов, планирует следующие шаги, может писать и исполнять код, использовать инструменты и менять стратегию по ходу работы. Допускается как один агент, так и несколько агентов с разными ролями (стр. 13).

AutoResearch — это цикл: **гипотеза → эксперимент → оценка на валидации → сохранить улучшение либо разобрать неудачу и выбрать следующую гипотезу**. Пример из PDF — гипотеза о производном признаке «возраст здания», затем кодирование и сравнение модели по метрике (стр. 14–15). Для кейса важна не просто автоматическая сетка моделей, а автономное исследование с учётом того, что агент уже пробовал. Одновременно PDF предупреждает о подгонке к метрике: LLM может оптимизировать наблюдаемый показатель в ущерб реальному качеству, поэтому решение должно принимать изменения по объективному результату валидации (стр. 13, 15).

### Регрессия

Локальные данные соответствуют указанным размерам и назначению: 62 признака, `site_eui` и `id`; test содержит те же признаки и ID без таргета. Фактический порядок последних колонок train — `site_eui`, затем `id`; в шаблоне сабмита порядок — `id`, `site_eui`. Поэтому следует ориентироваться на имена и роли полей, а не позицию колонки.

В данных есть пропуски: `year_built` — 1 727; `energy_star_rating` — 22 222; `direction_max_wind_speed` — 26 309; `direction_peak_wind_speed` — 27 038; `max_wind_speed` — 26 309; `days_with_fog` — 32 928 строк train. В test пропуски есть в тех же шести полях: `year_built` — 110; `energy_star_rating` — 4 487; `direction_max_wind_speed`, `direction_peak_wind_speed` и `max_wind_speed` — по 14 773; `days_with_fog` — 12 868. Данные описывают здание и годовое наблюдение, включая погоду за тот же год; согласно `task.md`, это оценка при уже известной фактической погоде, не прогноз до наступления года.

### Многоклассовая классификация

В train 42 признака, ID и `attack_cat`; в test — те же признаки и ID. Классы в train существенно несбалансированы: `Normal` 28 000, `Generic` 20 000, `Exploits` 16 696, `Fuzzers` 9 092, `DoS` 6 132, `Reconnaissance` 5 245, `Analysis` 1 000, `Backdoor` 873, `Shellcode` 567, `Worms` 65. В CSV фактически нет пустых значений, хотя `task.md` допускает пропуски в категориальных полях. Категориальные признаки — `proto`, `service`, `state`; их число уникальных значений в train вместе с возможным пропуском равно 133, 13 и 9. Значение `-` в `service` означает отсутствие сервиса. Поле `label` отсутствует — это отдельно объяснено в `task.md` как исключение бинарной метки, способной утечь в ответ.

Колонка `id` здесь перенумерована с нуля отдельно в обоих файлах: train — 0…87 669, test — 0…41 165. Поэтому все ID test численно встречаются в train; это не ключ для связывания строк между выборками. Сопоставление строк по числовому ID не выявило идентичности записей: полностью совпали признаки лишь у одной из 41 166 пар с одинаковым ID. ID нужен для вывода и проверки порядка.

## 4. Проверка `baseline.py` и `requirements.txt`

Локальный `baseline.py` — небольшой пример LLM-агента с Python-инструментом. Он читает путь к `task.md` из первого аргумента, по умолчанию берёт `task.md`, требует `OPENAI_MODEL`; в комментарии запуска перечислены `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL`. Агент делает последовательные вызовы Chat Completions с отключёнными параллельными tool calls, максимум 100 циклов. Инструмент `run_python` выполняет код в новом процессе с рабочим каталогом папки задачи; файловая система сохраняет состояние, память процесса — нет. Один вызов Python ограничен 1 800 секундами; в ответ возвращаются последние 12 000 символов stdout/stderr и код выхода. В дочернем процессе явно остаются только `PATH` и `PYTHONIOENCODING` из переменных окружения.

В текущем файле **нет** создания или проверки `submission.csv`, валидатора его колонок, описания путей платформенных входов/выхода или кода, который интерпретирует формат сабмита. В промпте агента говорится решить задачу через `run_python`; финальный ответ агента печатается в stdout. Следовательно, утверждение PDF, что полный платформенный контракт закреплён в `baseline.py`, не подтверждается переданной копией этого файла. Также приложение 2 называет запускаемый файл `script.py`, тогда как PDF требует `solution.py` в ZIP, а локальный пример называется `baseline.py` (стр. 6, 17).

`requirements.txt` фиксирует Python 3.12 и версии NumPy, pandas, sklearn, CatBoost, LightGBM, XGBoost, imbalanced-learn, Optuna, PyTorch, AutoGluon, LightAutoML, FLAML, OpenAI SDK и других библиотек. В файле **нет** пакета `mcp`, хотя `baseline.py` импортирует `mcp` (строки 11–13). Если эти требования — полный список установленных зависимостей, baseline не запустится без дополнительной зависимости; возможно, `mcp` предоставляется отдельно — это не пояснено. Для платформы также не указано, устанавливаются ли все библиотеки из списка или только выбранная часть.

## 5. Практические выводы для MVP — рекомендации, не требования PDF

1. Сначала сделать надёжный контракт исполнения: единый `solution.py`, поиск task-файла и таблиц по фактическому интерфейсу, чтение словаря и `sample_submission.csv`, затем проверка результата по шаблону (строки, порядок ID, названия колонок, допустимые метки, конечные числовые значения). Сейчас именно этот контракт не удаётся восстановить из локального baseline.
2. Начать с устойчивого табличного решения, управляемого структурой задачи и её метрикой. Сохранять резервный валидный результат до дорогих экспериментов, измерять каждый вариант на локальной валидации, выбирать по метрике кейса и переобучать лучшую конфигурацию на всех train-данных перед test. Это рекомендация, а не отдельное требование организаторов.
3. Валидация должна отражать то, что известно о данных. Для многоклассовой задачи Macro F1 требует внимания к редким классам, включая всего 65 примеров `Worms`; обычная accuracy может выглядеть хорошо при слабом результате на редких классах. Для регрессии RMSE чувствителен к большим ошибкам и крупным выбросам таргета. Валидационную стратегию стоит явно выбирать и документировать, не подглядывая в test-метки.
4. В ограничении 3 часов оставить время на чтение входа, обучение финальной модели, запись и проверку файла. Ограничивать число LLM-итераций и максимальное время эксперимента; сохранять метрики/гипотезы и лучшую конфигурацию вне RAM, так как процессы инструмента baseline перезапускаются.
5. Не зашивать имена публичных столбцов и конкретную модель как единственный путь. Приватные задания новые, и цель требует повторного применения без изменения кода. При этом заранее неизвестно, гарантированы ли приватные задачи как табличные supervised CSV-задачи.
6. Учитывать только разрешённые входы и инструменты. Сеть внутри контейнера запрещена, внешние LLM-ключи запрещены; разработка на собственной инфраструктуре не означает, что в решении можно скачать данные или предобученные веса.
