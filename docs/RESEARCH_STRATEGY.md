# Выбор моделей и бюджет исследования

## Что реализовано

Host читает данные, строит профиль и сохраняет `strategy.json`: размер таблиц, категории, кардинальность, пропуски, infinity, частоты классов, доступные библиотеки, shortlist и лимиты. При числе классов больше 30 частоты ограничены, а отношение частот помечается как частичное.

До LLM сравниваются три семейства: CatBoost, ExtraTrees и линейная модель (LinearRegression или LogisticRegression). У всех один seed, один holdout и host-owned метрика. Preprocessing входит в pipeline и обучается только на обучающей части. CatBoost использует категории, деревья и линейная модель — sparse-compatible кодирование. `family_comparison.json` содержит измерения и выбранный trial, а LLM получает их вместе с кодом победителя. Недоступные семейства пропускаются. Явный `--family-trials 1` включает прежний baseline с fallback CatBoost → ExtraTrees.

Общий `--max-trials` включает начальные семейства, ошибки, отменённые и LLM-опыты. В LLM-режиме полное запрошенное сравнение запускается, только если после него остаются хотя бы два trial; иначе используется один baseline. В offline-режиме весь лимит можно потратить на сравнение семейств. Низкий общий бюджет может прервать сравнение до завершения всех кандидатов.

LLM передаёт гипотезу и публичное `decision`: наблюдения, семейство, обоснование, альтернативы, ожидаемый эффект, риски и оценку прошлого результата. Поле необязательно для совместимости; его отсутствие явно отмечается. Host независимо оценивает результат, сохраняет фактическую цепочку estimator и объясняет принятие или отклонение. Заявленное семейство и фактический backend могут отличаться; оба видны в артефактах.

## Почему сравниваем семейства

CatBoost — сильный начальный кандидат для смешанных таблиц благодаря обработке категорий; см. [официальное описание](https://catboost.ai/docs/en/concepts/algorithm-main-stages_cat-to-numberic). Однако победитель зависит от данных, бюджета, настройки и валидации: [TabArena](https://arxiv.org/abs/2506.16791). Поэтому выбор делается по измеренной целевой метрике. Предобученные табличные модели не используются: кейс запрещает внешние pretrained-модели.

Для Macro F1 важно отдельно проверять обычный и взвешенный loss и ошибки редких классов. Class weights не гарантируют улучшения. Один выигрыш на holdout также не доказывает статистическую значимость; при большом числе гипотез возможен подбор под валидацию.

## Время и адаптивный резерв

Диагностика выполняется один раз, после неё запускаются короткое сравнение семейств и целевые LLM-опыты. Процентных квот на диагностику и каждое семейство нет: их ограничивают общий бюджет и timeout каждого опыта.

Начальный резерв финализации — 15% общего времени, без прежнего потолка 600 секунд. После каждого принятого результата рассчитывается план для текущего победителя:

```
row_scale = full_train_rows / actual_fit_rows
estimated_fit_seconds = trial.seconds × row_scale × 1.5
write_margin = max(5 seconds, 1% total_budget), не выше total_budget
reserve = min(total_budget, max(5% total_budget, estimated_fit_seconds + write_margin))
```

`trial.seconds` — длительность всего evaluation-процесса, включая чтение данных и предсказания. Это консервативная оценка стоимости refit, а не замер только `model.fit`. Рост стоимости обучения может быть нелинейным, поэтому оценка не гарантирует завершение. При неуспешном или отсутствующем измерении сохраняется начальный резерв. План воспроизводится из durable результата; события `reserve_updated` показывают изменения. Если оценка не помещается в общий лимит, `feasible=false`.

Исследование останавливается при входе в резерв. Финальное обучение получает оставшееся общее время за вычетом запаса на запись; исследовательский `--trial-timeout` к нему не применяется. При ошибке финального обучения остаётся последний валидный submission, полученный от модели на train split, а в отчёте виден сбой refit.

Текущий host строит фиксированный случайный holdout, со стратификацией для классификации, когда она возможна. Временные и групповые split автоматически не определяются; такие задачи требуют расширения host.

## Два параллельных worker

По умолчанию активны до двух ML-процессов, каждому передаются четыре CPU-потока. Один LLM-исследователь может отправить две независимые гипотезы через `run_experiments`; одиночный `run_experiment` остаётся совместимым. Три начальных семейства проходят через ту же очередь: два активны, третий ждёт. Два trial не должны зависеть от ещё неизвестных результатов друг друга.

Admission проверяет максимум два процесса, суммарно ≤8 `n_jobs` и ≤28000 MB объявленных RSS-лимитов. По умолчанию RSS-лимит одного worker 12000 MB. Каталоги и manifest раздельны; только координатор назначает IDs, пишет журнал, проверяет метрики и публикует CSV. При равной метрике выбирается меньший числовой trial ID независимо от порядка завершения. Точные интервалы subprocess, PID и `n_jobs` сохраняются в `process.json`.

Deadline, остановка и исключение координатора отменяют активные и ожидающие работы, supervisor завершает process group. Ошибка одного кандидата не отменяет успешный результат второго. При resume исход неизвестного начатого trial фиксируется как interrupted; автоматического повторения side effects нет. LLM usage учитывается один раз на ответ, включая пакетный tool.

Потоки задаются через окружение и model context. Это ресурсный scheduler с supervisor, а не OS sandbox для произвольного Python. Жёсткую изоляцию CPU, памяти, файлов и сети обеспечивает контейнер или другая среда запуска.

Отдельные LLM-исследователи пока не добавлены. Для их обоснования нужна ablation с одинаковыми задачами, seeds и бюджетами: качество, успешные опыты, время, токены и разнообразие моделей. Несколько клиентов одной локальной Ollama сами по себе не дают больше вычислений.

## Где читать решения

- `agent.log`: читаемая хронология; для наблюдения используйте `tail -F`, поскольку проекция заменяется атомарно.
- `decisions.jsonl`: структурированные решения с номерами исходных событий.
- `events.jsonl`: первичный durable-журнал запросов, инструментов, usage, ошибок и результатов; известный API-ключ редактируется.
- `family_comparison.json`: исходное сравнение семейств; позднейшие LLM-кандидаты отражены в experiments/report.
- `trial_XXXX/decision.json`, `code.py`, `process.json`, `worker_result.json`: объяснение, реализация, выполнение и фактическая модель.
- `experiments.json`, `report.json`, `report.md`: метрики, окончательный победитель, резерв, refit и пути артефактов.

Публичные объяснения описывают решения и наблюдаемые действия. Скрытые внутренние рассуждения провайдера не запрашиваются. Старые запуски восстанавливают проекции имеющихся событий; отсутствующие объяснения LLM задним числом не создаются. Пропущенная оценка host восстанавливается по сохранённой метрике с явной отметкой и без повторного обучения.
