# Выбор моделей и бюджет исследования

## Что реализовано

До первого LLM-запроса host читает данные, строит профиль и сохраняет `strategy.json`: число строк и признаков, категории, кардинальность, пропуски, infinity, отношение частот классов, доступные библиотеки, короткий список моделей и направления опытов. При числе классов больше 30 частоты в профиле ограничены, и отношение частот помечается как частичное.

Начальный baseline использует CatBoost при доступной библиотеке; при ошибке импорта/обучения он переходит на ExtraTrees с preprocessing. Для преимущественно числовой таблицы стратегия предлагает сравнение с HistGradientBoosting, при большом числе признаков — с регуляризованной линейной моделью. Это эвристический shortlist: автоматического соревнования всех семейств до LLM-цикла пока нет. Наличие категории не доказывает преимущество CatBoost, а число признаков не доказывает линейность зависимости.

LLM получает профиль, shortlist, рабочий код, реальные метрики и ошибки. В каждом `run_experiment` она должна передать `decision`: наблюдения, выбранное семейство, обоснование изменения, альтернативы, ожидаемый эффект, риски и оценку прошлого результата. Поле необязательно на уровне протокола для совместимости со старыми ответами и провайдерами; при его отсутствии журнал прямо сообщает, что подробное объяснение не предоставлено.

Host независимо запускает код, оценивает его на одном holdout и пишет, почему кандидат принят или отклонён. Ожидание LLM не считается измерением; один выигрыш на holdout не доказывает статистически значимое преимущество. Worker сохраняет фактическую цепочку estimator: wrapper → pipeline → обученный алгоритм. Она может отличаться от заявленного семейства. Штатный baseline также сохраняет `fallback_reason`, если пришлось перейти с CatBoost на ExtraTrees. Для нового LLM-кода prompt требует не скрывать ошибки сменой алгоритма; если автор всё же реализовал fallback без объяснения, фактический класс остаётся виден, но причина может отсутствовать.

## Почему CatBoost первым, но без гарантии победы

CatBoost специально обрабатывает категории с помощью статистик, включая комбинации признаков; это полезный старт для смешанных табличных данных. См. [официальное описание обработки категорий](https://catboost.ai/docs/en/concepts/algorithm-main-stages_cat-to-numberic).

Сравнение TabArena показывает, что результат зависит от бюджета, способа валидации, настройки и ансамблирования. Бустинг остаётся сильным кандидатом, однако универсального победителя для любой таблицы нет. См. [исследование TabArena](https://arxiv.org/abs/2506.16791). Предобученные табличные модели из подобных сравнений не предлагаются для этого кейса: правила запрещают внешние pretrained-модели.

Для Macro F1 дисбаланс стоит исследовать явно: сравнивать обычный и взвешенный loss, смотреть ошибки по классам. Веса могут улучшить редкие классы и ухудшить другие, поэтому победителя определяет целевая метрика, а не наличие class_weights в коде.

## Предлагаемое распределение трёх часов

Это рекомендация для следующего развития scheduler, а не уже включённые квоты:

1. Около 5–10%: диагностика данных и проверка схемы валидации, утечек, категорий, пропусков, дисбаланса. Если есть время или группы, сначала определить корректный split.
2. Около 75–80%: короткое сравнение 2–3 семейств на одной валидации, затем целевые опыты вокруг лучших кандидатов. Увеличивать число итераций после измерения стоимости обучения. Не тратить весь бюджет на вариации одной модели без проверки альтернатив.
3. Около 10–15%: финальное обучение на всём train, контроль submission и сохранение артефактов. Резерв уточнять по времени лучших опытов и росту train.

Сейчас диагностика выполняется один раз перед исследованиями, обучение идёт последовательно, финализация зарезервирована правилом `min(600 seconds, max(1 second, 15% total_budget))`. Фактические лимиты видны в `strategy.json` и `agent.log`. При лимите 10800 секунд это 600 секунд, а не 15%. Полное финальное обучение дополнительно ограничено `--trial-timeout`. Изменять бюджетную политику нужно вместе с измерением стоимости refit, чтобы рекомендация не превратилась в лишний простой.

Текущий host использует фиксированный случайный holdout, со стратификацией для классификации, когда она возможна. Временные и групповые split автоматически не строятся. Запрос к LLM сам по себе этот выбор не меняет; для временной или групповой задачи необходимо расширить host до сравнения моделей.

## Когда нужны несколько исследователей

Пока лучше один исследователь, единый журнал и независимый evaluator. При локальной Ollama несколько исследователей делят одну модель, память и вычисления; обучение делит 8 CPU платформы. Само увеличение числа LLM-процессов не обеспечивает прирост качества.

Следующий проверяемый шаг: ограниченный параллельный запуск независимых ML-trials с общим split, ledger и ресурсным scheduler. Например, два trial по 4 CPU при достаточной памяти и поддержке backend. Сначала измерить выигрыш по времени и качеству относительно последовательного запуска при одинаковых CPU-часах и числе LLM-токенов.

Роли «аналитик данных», «автор гипотез» и «критик» можно первоначально реализовать этапами одного агента. Отдельных LLM-агентов стоит добавлять после ablation: одинаковые задачи, бюджеты и seeds; сравнение целевой метрики, доли успешных опытов, времени, токенов и разнообразия моделей. Новая runtime-мультиагентная архитектура в текущем изменении не вводится.

## Где читать решения

- `agent.log`: читаемая хронология, обновляется во время запуска и выводится в stderr.
- `decisions.jsonl`: структурированная проекция решений и действий с исходными номерами событий.
- `events.jsonl`: первичный durable-журнал, включая запросы, tool-вызовы, usage и результаты; известный API-ключ редактируется.
- `trial_XXXX/decision.json`: объяснение выбора конкретного опыта.
- `trial_XXXX/code.py`, `process.json`, `worker_result.json`: реальная реализация, stdout/stderr и фактическая модель.
- `experiments.json`, `report.json`, `report.md`: метрики, выбранный trial и итоговые пути.

Публичные объяснения — проверяемое описание решений для пользователя. Скрытые внутренние рассуждения провайдера не запрашиваются и не являются журналом. Старые запуски могут восстановить проекции имеющихся событий, но объяснения, которых тогда не было, задним числом не появятся.
