# DeepSeek Harness: выполнение, надёжность и перенос в ML AutoResearch

Срез исходников: `deepseek-ai/deepseek-harness`, ветка `master`, commit [`687f282e8625c6b8d11ff58211a90524be2e4317`](https://github.com/deepseek-ai/deepseek-harness/commit/687f282e8625c6b8d11ff58211a90524be2e4317), от 17 октября 2026. Ниже описан именно этот снимок исходников, а не предположения о возможностях Harness вообще.

## Вывод для MVP

В Harness есть зрелые инженерные шаблоны для исполнения кода: отдельный управляемый процесс по умолчанию, отмена и завершение потомков, дедлайны, ограничение вывода, очистка окружения, файловые политики, классификация ошибок, тестирование отказов и журналирование критичных границ до внешнего эффекта. Также есть журнал с контрольными точками для возобновления сессий.

Это не готовая основа AutoML-исполнителя. Реализованный PTC runtime принимает модельный **TypeScript** и запускает Node.js, не Python 3.12; он не предлагает лимит CPU или надёжный лимит памяти всего дерева процессов. В Harness нет встроенного цикла экспериментов, сравнения моделей на заданной ML-метрике, валидации Kaggle-подобной отправки или хранилища артефактов обучения. Эти части надо строить вокруг Python-runner для текущего кейса.

## Что именно уже есть в Harness

### Код выполняется отдельно от процесса агента

`@deepseek-ai/dsh-ptc-runtime-node` по умолчанию запускает свежий Node-процесс для каждого вызова; сохраняются файлы, но не переменные. Необязательный режим `persistent-in-memory` оставляет REPL на время жизни агента, но теряет память при отмене, таймауте, сбое или завершении владельца; это не сохранённая на диск Python-сессия ([README runtime, `Summary` и ограничения](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/README.md#L10-L13), [описание режимов и потери состояния](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/README.md#L67-L84)).

Код и ответы обменяются через отдельный length-framed JSON control pipe. Хост проверяет тип, идентичность и порядок вызовов объявленных bindings, формат JSON и размеры сообщений; некорректный или слишком большой трафик завершает выполнение с `protocol`-ошибкой. Код не получает переменные окружения хоста. Результат содержит сохранённые логи и JSON-значение, а не живой объект Python ([`NodePtcRuntime.execute`](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/src/index.ts#L200-L243), [`JsonChannel`](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/src/channel.ts#L1-L130)).

### Лимиты и отмена покрывают сам вызов, но не весь бюджет агента

В runtime-конфигурации по умолчанию: дедлайн вызова 120 секунд и максимум 600 секунд, лог/результат 64 MiB, V8 old-generation heap 512 MiB, control-frame/очередь 128 MiB, до 128 одновременных host bindings и 3 секунды на остановку и drain потоков. Дедлайн охватывает запуск, исполнение и ожидание вложенных bindings/approval; явный `null` отключает его. При отмене, таймауте, завершении вызова или выгрузке provider runtime останавливает управляемый процесс и дренирует stdout/stderr ([конфигурация](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/src/config.ts#L6-L61), [`resolve`/`execute` и выбор результата](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/src/index.ts#L76-L195), [остановка и drain](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/src/output-stream.ts#L11-L49)).

Это **elapsed wall timeout**, не CPU-счётчик. V8 heap cap не учитывает нативные выделения, дочерние процессы и их память. В документации прямо указано отсутствие process-tree CPU meter и process-tree memory limit ([ограничения runtime](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/README.md#L158-L170)). Для Python + NumPy/CatBoost/PyTorch лимит самого интерпретатора или `resource`-настройка одного процесса не заменяет общий лимит контейнера/cgroup на группу процессов.

Сбой runtime получает различимый класс: `exception`, `timeout`, `abort`, `protocol`, `sandbox-unavailable`, `worker-exit`, `invalid-output` или `output-limit`. При переполнении возвращается явная ошибка и ограниченный префикс лога; итоговый JSON проверяется на lossless-представимость. Леджер считает сериализованный stdout/stderr, completion/diagnostic вместе; результаты вложенных binding-вызовов в этот лимит не включены ([классификация результата](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/src/index.ts#L165-L189), [`OutputLedger`](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/src/output-ledger.ts#L1-L65)).

### Есть файловая изоляция, но это не сетевой sandbox

Sandbox policy разрешает `read-only`, `workspace-write` с конкретным корнем или `danger-full-access`. Решение передаётся каждому вызову; для обычной сессии корень берётся из её cwd. На Linux provider выбирает bubblewrap либо Landlock, на macOS — Seatbelt, на Windows — ACL runner. Если ограничивающий backend недоступен, вызов в ограниченном режиме завершается с ошибкой вместо тихого запуска без sandbox. Enforcement может сообщаться как `partial`; Windows ACL и некоторые ABI Landlock имеют оговорённые исключения ([политика и корень сессии](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/sandbox/sandbox-policy/src/index.ts#L104-L180), [выбор и полнота backend](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/sandbox/sandbox-local/src/index.ts#L151-L189), [fail-closed и ограничения](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/sandbox/sandbox-local/README.md#L10-L57)).

Политика Harness относится к **файловым эффектам**. Документация указывает, что сеть и видимость процессов вне этой модели. Следовательно, для данного offline-контейнера доступ без интернета должен обеспечиваться самим контейнером/средой; sandbox не гарантирует его. Проверки путей и symlink для файловых инструментов полезны, но README прямо отличает их от kernel boundary для недоверенного кода ([проверка файловых мутаций](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/fs/fs-sandbox/src/index.ts#L10-L23), [ограничения словаря sandbox](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/sandbox/sandbox/src/index.ts#L24-L30)). Встроенный Node-runtime здесь можно использовать как архитектурный пример, но не как замену изоляции Python-кода.

### Процессы, потомки и сбор вывода управляются отдельно

Subprocess provider поддерживает OS-managed группы/диапазоны процессов и терминальные сессии, scrubbed environment, ограниченный хвост stdout/stderr и необязательный spill полного вывода в закрытую временную директорию. На Linux усиленное владение зависит от доступности user-systemd; на fallback-хостах потомок, успевший отвязаться/переподчиниться, может выйти из наблюдаемого дерева. macOS использует fallback. Это хорошая модель управления ресурсами, но не безусловная гарантия для любого процесса на любом хосте ([README subprocess](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/subprocess/subprocess-local/README.md#L10-L18), [сбор потока](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/subprocess/subprocess-local/README.md#L45-L49), [условия владения и ограничения fallback](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/subprocess/subprocess-local/README.md#L141-L158)).

### Повторяются только модельные запросы; журнал не означает exactly-once

У LLM retry-плагина по умолчанию конечная политика: до пяти повторов только для пустого ответа, rate limit, server, timeout и transport; backoff ограничен 500 мс–10 с с jitter. Каждый повтор — новый оплачиваемый запрос. Режим `always` существует, но продолжает без лимита попыток до успеха, отмены или выгрузки и может крутиться на постоянной ошибке; для ограниченного по времени MVP он непригоден. Это retry модели, а не повтор Python training job ([README retry](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/llm/llm-retry/README.md#L10-L58), [режимы и значения по умолчанию](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/llm/llm/src/retry-policy.ts#L14-L24)).

`session-checkpoint-policy` сбрасывает в persistence журнал запроса перед вызовом модели, записанный вызов инструмента — перед его телом, и результат шага — до следующего запроса. При падении между dispatch и result сохраняется неизвестный исход; внешний эффект автоматически не запускается повторно, потому что он уже мог произойти. Для побочных эффектов предлагается передавать `callId` как idempotency key, где это поддерживается ([реализация checkpoint](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/session/session-checkpoint-policy/src/index.ts#L20-L82), [что гарантируется и ограничения](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/session/session-checkpoint-policy/README.md#L46-L53), [unknown outcome и exactly-once](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/session/session-checkpoint-policy/README.md#L93-L116)).

## Что показывает текущий baseline и где границы

В [baseline.py](../../baseline.py#L24-L42) `run_python` уже использует отдельный процесс текущего Python 3.12, запускает его с cwd каталога задачи и не передаёт дочернему коду ключи/секреты родительского окружения. Но `capture_output=True` накапливает **весь** вывод в памяти и только потом отдаёт последние 12 000 символов каждой стороны; это не streaming cap. Таймаут 1 800 секунд применяется на вызов, а не на весь запуск. `subprocess.run(timeout=...)` останавливает запущенный child; в этом коде нет создания/остановки отдельной process group для потомков ([Python 3.12 subprocess docs](https://docs.python.org/3.12/library/subprocess.html)). Нет отдельного лимита CPU/RSS/disk, фиксируемого trial budget или проверки, что завершились все дочерние процессы. Workspace-каталог задачи одновременно содержит задачу и входные данные, отдельный writable output sandbox не выделен.

В `run_agent` лимит в 100 итераций — единственный явный стоп-счётчик. Общего 3-часового wall deadline, модели стоимости/числа токенов, числа экспериментов, дедлайна API-запроса в коде и финального резервного окна нет. Обрабатывается только `ValueError` от tool call; таймаут кода возвращается как обычная строка ошибки. Запись истории живёт в памяти процесса, возобновляемого trial journal и manifest эксперимента нет ([цикл и обработка tool result](../../baseline.py#L44-L82)).

Важный контекст: кейс уже поставляет табличные CSV на 53–88 тыс. обучающих строк и требует точный submission contract, Macro F1 для классификации или RMSE для регрессии. Данные и контракт описаны в [`task.md` классификации](../../Многоклассовая%20классификация/task.md#L15-L30) и [`task.md` регрессии](../../Регрессия/task.md#L11-L24). Поскольку платформа офлайн, установку библиотек и скачивание моделей нельзя оставлять на инициативу агента во время выполнения; `requirements.txt` закрепляет Python 3.12 и версии ML-пакетов ([requirements](../../requirements.txt#L1-L48)).

## Переносимые меры для MVP (3 часа, 8 CPU, 32 GB RAM)

### P0 — до первого запуска модельного кода

1. **Один supervisor владеет общим бюджетом.** Дедлайн 3 часа ставится при старте и включает LLM-запросы, ожидание tool, subprocess cleanup и итоговую проверку. У каждого эксперимента отдельный более короткий wall timeout (для MVP начать с 10–15 минут и менять после замера). Резервировать последние 10 минут для воспроизводимого финального fit, проверки артефактов и записи submission. На старте — один training child одновременно; число BLAS/OpenMP/CatBoost worker-потоков ограничить конфигурацией так, чтобы суммарно не выходить за 8 CPU. Не выдавать каждому вызову отдельный независимый лимит в 3 часа.

2. **Исполнять Python-код через управляемую границу процесса.** Использовать argv без shell-конкатенации, `sys.executable` заданного Python 3.12, свежий процесс для каждой попытки/эксперимента и task workspace как cwd. Таймаут должен убивать весь process group/job, включая дочерние training процессы. Контейнер ограничивает сеть, а контейнер/cgroup — CPU и RAM; с учётом локального Ollama заранее делить 32 GB между моделью, Python и системой. Отмена, timeout, OOM и exit code возвращаются как структурированные поля, а не только текстом.

3. **Сделать отдельный workspace и ограничить I/O.** Монтировать входные данные и task spec только для чтения; создать на run новый каталог `artifacts/<run_id>/<trial_id>` с правом записи. Выходы агента не должны попадать за этот корень. Запретить установку пакетов и скачивание файлов во время trial; offline-среда/allowlist должна быть проверена фактически. Не передавать `OPENAI_API_KEY`/секреты в Python child. Нужен именно process/container boundary для произвольного Python: простая проверка пути на уровне API не ограничивает `open()`, `subprocess` или нативные библиотеки.

4. **Ограничить память stdout и stderr во время чтения.** Потоки читаются инкрементально в capped buffer/tail, превышение фиксируется как `output_limit`, child останавливается. Не собирать неограниченный вывод в RAM перед обрезкой. Сохранять указатель на полный файл только при наличии жёсткого disk cap и per-trial каталога; default — хвост диагностики и логический лимит на размер артефактов.

5. **Каждая ML-попытка получает оценку только на train/validation.** Не открывать тестовую метку; зафиксировать seed и split до запуска. Для каждого trial хранить метрику, время, статус, параметры, версию/хеш исходного скрипта и использованные входы. Финальная проверка schema, колонок, id, допустимых классов/числовых предсказаний, количества строк, порядка строк, NaN/inf, размера CSV и успешного `read_csv` обязательна перед `completed`. Создать/публиковать submission атомарно, чтобы прерванная запись не выглядела готовой.

6. **Ограничить повтор модели отдельно от повторов исполнения.** Для Ollama/Qwen API задать конечные retries, timeout и max tokens на запрос; повторять только временные 429/5xx/network timeout. Не повторять автоматически ошибку кода/400/auth или потенциально завершённый training call. Каждый вызов и задержка уменьшают общий deadline. Не использовать unbounded `always` retry.

### P1 — если остаётся время после устойчивого happy path

- Вести JSONL ledger событий `run_started`, `llm_request`, `tool_dispatched`, `trial_started`, `trial_finished`, `artifact_written`, `budget_stop`. Событие `trial_started` сбрасывать до запуска кода; после crash незакрытый trial отмечать `outcome_unknown`, проверять его каталог и не повторять побочный эффект вслепую. Идемпотентность через уникальные `run_id/trial_id` и атомарную публикацию артефактов.
- Сохранять для воспроизведения каждый script, manifest, stdout/stderr bounded tail, structured failure, CPU/wall/memory peak, seed, версия Python и доступные версии пакетов, command argv и checksum файла. Убирать ключи/персональные данные из истории.
- Считать retryable и non-retryable сбои разными классами: transient API failure → bounded backoff; Python exception → вернуть traceback и разрешить модели одну осмысленную коррекцию; повтор одной и той же ошибки/скрипта — остановить или запросить новый план. Пер-experiment retries включить только после проверки, что запуск идемпотентен.
- Для CLI дать одну команду запуска и по завершении краткую машинно-читаемую сводку: `run_id`, статус/stop reason, лучшая измеренная Macro F1/RMSE, путь к submission и журналу. Расширить evals с малых синтетических CSV до локальных smoke-run обоих кейсов; записать метрики и проверить submission contract. Ранжировать по требуемой метрике (Macro F1/RMSE), не по общей Accuracy или удачному stdout. Численный порог качества не задан: не придумывать pass/fail порог; выдавать воспроизводимый результат и сравнение с простым baseline.

## Сценарии приёмки

| Сценарий | Что должно произойти |
|---|---|
| Скрипт зависает в бесконечном цикле | Trial deadline наступает, весь process group завершён, результат `timeout`, supervisor продолжает либо завершает run по общему бюджету. |
| Код печатает гигабайты | Память процесса не растёт пропорционально выводу; срабатывает byte cap, сохраняется диагностика с `output_limit`, процесс прекращается. |
| Код создаёт дочерний процесс и зависает | После timeout не остаётся живых потомков; проверка делается по process group/container, а не только PID Python. |
| Код пытается читать/писать за task workspace | Чтение входов проходит; запись входного каталога и traversal/symlink наружу блокируются реальным OS/container sandbox. Run не продолжает работу в режиме без sandbox, если он обязателен. |
| Код расходует память или CPU сверх бюджета | Контейнерный лимит останавливает процесс; событие содержит resource-limit причину, общий supervisor сохраняет управление. Проверить также native/threaded workload. |
| Неверный импорт/синтаксис/исключение | Exit code и bounded traceback структурированы; нет автоматического повтора ошибки как инфраструктурного сбоя. В модели нет скрытого объявления trial успешным. |
| LLM получает 429, 500, timeout, 401 или невалидный запрос | На временные ошибки — конечный retry с jitter в рамках остатка deadline; на постоянные ошибки — немедленный fail-fast; отмена прерывает ожидание. |
| Supervisor падает во время trial | При возобновлении незавершённый `trial_id` помечается неизвестным; не дублируется запуск до проверки артефактов и состояния процесса. |
| Предсказание с пропуском, неверным классом, дубликатом id или переставленными строками | Валидатор отклоняет submission; run не помечается завершённым и не заменяет последнюю валидную версию. |
| Валидационная метрика не улучшается, но модель сообщает успех | Метрика и контракт вычисляются кодом evaluator, независимым от текста/самооценки модели; лучший trial остаётся выбранным по целевой метрике. |
| Общий лимит 3 часа истекает при ожидающем tool | Supervisor прекращает активный child, закрывает текущий trial как timeout/aborted и оставляет резерв для проверки/сохранения итогов. |

## Что можно заимствовать, а что нельзя переносить напрямую

Заимствовать стоит разделение host-supervisor и недоверенного child, per-call политики, явные error kinds, bounded output ledger, раздельные лимиты, cleanup, fail-closed sandbox, durable intent перед внешним действием и тесты на зависания/overflow/cancellation/crash. В Harness это подтверждено отдельными тестами на таймаут синхронного цикла, отмену и завершение потомка, output cap и heap потолок (`ptc-runtime-node/tests/runtime.spec.ts`), sandbox policy при persistent REPL (`persistent-sandbox.spec.ts`), отказ launcher и cleanup (`host-failures.spec.ts`), а также crash recovery checkpoints (`session-checkpoint-policy/tests/crash-recovery.e2e.ts`). Например, runtime-тест прямо проверяет, что управляемый потомок закрылся до возвращения результата, а отдельный тест показывает, что heap setting проверяет только V8 ([runtime tests](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/ptc-runtime/ptc-runtime-node/tests/runtime.spec.ts#L150-L221)).

Не следует считать эти тесты eval-ами качества ML-агента. Они проверяют корректность runtime и Harness, не Macro F1/RMSE, подбор модели, leakage, воспроизводимость AutoML или готовность submission. В репозитории есть настоящие интеграционные/отказные тесты retry и session persistence, но по ним нельзя сделать вывод, что агент правильно решает табличные задачи ([retry tests](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/llm/llm-retry/tests/transport-recovery.spec.ts#L101-L170), [checkpoint crash test](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/session/session-checkpoint-policy/tests/crash-recovery.e2e.ts#L1-L120)). Для MVP нужны собственные task fixtures и независимый evaluator.

Границы переноса: исходники — большой TypeScript/Node plugin app со множеством Cordis-сервисов; не нужно тянуть его runtime/зависимости в этот Python-проект за 3 часа. Скопировать архитектурные контракты и реализовать минимальный Python supervisor вокруг уже доступного Python 3.12. Оффлайн-контейнер остаётся enforce-слоем для сети и общих CPU/RAM; модель в Ollama или будущий OpenAI-compatible Qwen API получает отдельные connect/read timeout и конечные retries.
