## Regression: четыре попытки остановились на API и форме данных

В `trial_0004/code.py:17-20` `_clean_numeric` явно сводит вход к `ndarray`. Следующий шаг в строке 44 индексирует этот массив строковым именем `X[col]`; worker trace подтверждает, что фактический объект уже индексируется только целочисленно. Поэтому модель не проверила ни индикаторы пропусков, ни log-преобразование площади.

`trial_0005` сначала отвергнут парсером из-за лишней закрывающей скобки (строка 33). Независимо от этой синтаксической ошибки, список `transformers_without_missing` и `branch_transformers` строился из двухэлементных кортежей. В `trial_0006` и `trial_0007` тот же неверный формат передан `ColumnTransformer` напрямую, а внешние ветви также местами состоят только из пары. Контракт scikit-learn требует тройку `(name, transformer, columns)` для каждого transformer. [Документация `ColumnTransformer` для scikit-learn 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.compose.ColumnTransformer.html).

Следствие: regression LLM trials не имеют validation-метрик. Из них нельзя делать вывод, что новая модель или идея с индикаторами пропусков переобучилась либо недообучилась; их фактически не обучили. Ошибки исправлялись генерацией ещё одного полного свободного pipeline, а не заменой только сломанного узла на проверенный preprocessing.

## Classification: конфигурация отличалась от baseline, веса не доходили до fit

Baseline `trial_0001` сохраняет `iterations=150`, но не задаёт `learning_rate`. В коде нет явного LR; `CatBoostClassifier.get_params()` его не возвращает. После чтения сохранённой модели через `get_all_params()` фактический LR равен **0.4882799983**, `depth=6`, `l2_leaf_reg=3`, `border_count=254`, `auto_class_weights=None`, `class_weights=None`. Run metadata содержал только класс/цепочку estimator, поэтому LLM не видел эту фактическую конфигурацию в baseline comparison. CatBoost документирует динамический LR и то, что `get_all_params()` возвращает также вычисленные defaults. [Параметры CatBoost](https://catboost.ai/docs/en/references/training-parameters/common), [`get_all_params`](https://catboost.ai/docs/en/concepts/python-reference_catboostclassifier_get_all_params).

Четыре успешно обученных CatBoost-варианта задали LR **0.05**, **0.05**, **0.03** и **0.02**. Это соответственно около 10%, 10%, 6% и 4% фактического LR baseline. `trial_0007` ещё и описывал l2=3 как добавленную регуляризацию, хотя в baseline l2 уже равнялся 3. `trial_0010` действительно поднял l2 до 7. Это факты о конфигурации, а не доказательство, что один параметр единолично вызвал падение score.

`trial_0005` и `trial_0006` реализовали один и тот же CatBoost: 300 деревьев, LR .05, l2=3, без весов; у обоих один и тот же сохранённый файл validation-предсказаний по SHA-256 и одинаковый score. В `trial_0006` код читает `context.get("y_train")`, но worker manifest содержит только `task_type`, `metric`, `target`, `classes`, `feature_columns`, `categorical_columns`, `seed` и `n_jobs`. В манифесте нет `y`, `train_y`, `y_train` или весов. Поэтому `sample_weight` становится `None` и в fit не передаётся.

В `trial_0008` та же недоступная выборка y оставила веса пустыми. Если бы они были вычислены, код поместил бы `sample_weight` в constructor `ExtraTreesClassifier`, хотя sklearn принимает его в `fit`; подходящая настройка класса в constructor — `class_weight`. [ExtraTreesClassifier для scikit-learn 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.ensemble.ExtraTreesClassifier.html). В сохранённой модели действительно `class_weight=None`. На validation `trial_0008` не распознал ни одного объекта пяти классов: DoS, Analysis, Backdoor, Shellcode, Worms. Это объясняет низкий Macro F1 как наблюдаемое следствие слабого recall редких классов, но не доказывает единственную причину между отсутствием весов, кодированием категорий и ограничениями деревьев.

`trial_0004` перепутал два API CatBoost: `class_weights` принимает явные веса классов, а строковые режимы балансировки задаются `auto_class_weights="Balanced"` или `"SqrtBalanced"`. Удалив ошибочный параметр в следующей попытке, модель не добавила корректную замену. [Официальные параметры CatBoost](https://catboost.ai/docs/en/references/training-parameters/common).

`trial_0011` уже содержит два независимых блокера: `build_model` снова ищет отсутствующий `train_y`, а затем передаёт `sample_weight` в constructor CatBoost. CatBoost принимает веса объектов в `fit(X, y, sample_weight=...)`; host вызывает только `model.fit(train_x, train_y.to_numpy())`. Это подтверждено и traceback `unexpected keyword argument 'sample_weight'`, и [официальной сигнатурой CatBoost `fit`](https://catboost.ai/docs/en/concepts/python-reference_catboostclassifier_fit). В sklearn `Pipeline` fit-параметр конечного estimator передаётся с префиксом имени шага, например `model__sample_weight`; [документация Pipeline 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.pipeline.Pipeline.html). В этой задаче безопаснее маршрутизировать веса через host API.

Две попытки заявляли early stopping. В `worker.py:276` host обучает estimator одним вызовом `model.fit(train_x, train_y.to_numpy())`, без `eval_set`. Сохранённые модели `trial_0005/0006` имеют `od_wait=100`, но по факту сохранили все 300 деревьев; `get_best_score()` содержит только метрику `learn`, нет validation-итерации остановки. В документации CatBoost `eval_set` указан как данные для overfitting detector и выбора лучшей итерации. Поэтому эти trials не проверяли раннюю остановку по host holdout. [Параметры `eval_set`, `sample_weight` и `early_stopping_rounds` у `fit`](https://catboost.ai/docs/en/concepts/python-reference_catboostclassifier_fit).

## Что можно заключить о качестве, а что остаётся гипотезой

Подтверждено: полный профиль задачи имел дисбаланс от 28 000 `Normal` до 65 `Worms` (430.77:1); метрика — Macro F1. На сохранённом holdout у baseline recall `DoS` 0.145 и `Worms` 0.154. У невзвешенных `trial_0005/0006` он снизился до 0.023 и 0.000. У `trial_0007/0010` recall DoS был 0.001/0.002, а Worms — нулевой. Следовательно, заявленное изменение «веса классов» не произошло и редкие классы не улучшились.

Сохранённые train-метрики CatBoost тоже согласуются с недообучением: baseline train MultiClass loss 0.3998, у `trial_0005/0006` 0.4604, у `trial_0007` 0.5189, у `trial_0010` 0.5342. Но это train logloss, а выбранная holdout-метрика — Macro F1; без кривых обучения и одинаковой метрики на train/validation этого недостаточно для строгого диагноза. Поэтому версии «LR слишком мал для данного числа итераций» и «дополнительная l2-регуляризация ухудшила слабые классы» — обоснованные гипотезы, не доказанная причина. Объяснение модели про overfitting мажоритарных классов проверкой не подтверждалось.

Сами validation-ухудшения измерены на одном фиксированном split: baseline 0.565019 против .512595, .512595, .455899, .302110 и .446670. Они доказывают отсутствие улучшения в этих запусках, но не гарантируют, что любая будущая конфигурация с такими семействами будет хуже.

## Что host и контекст должны гарантировать

1. Предлагать LLM нормализованный recipe, а host должен построить весь estimator/pipeline из проверенных шаблонов. До fit валидировать имя семейства, имена параметров, типы и диапазоны; `depth=-1`, неверную строку `class_weights="Balanced"`, constructor-level `sample_weight` и неподдерживаемый early stopping отклонять с точной подсказкой.
2. Разделить настройку estimator и fit-метаданные. Для CatBoost безопасно разрешать `auto_class_weights` с перечисленными значениями либо строгие явные `class_weights`; для ExtraTrees — `class_weight`. Если recipe использует `sample_weight`, host вычисляет веса только из `train_y` и явно маршрутизирует их в fit. Не добавлять target-массивы в `build_model(context)`.
3. Показывать в baseline и каждом результате фактические параметры обученной модели. Для CatBoost передавать параметры `get_all_params()` после fit, включая автоматический LR и веса; для известных sklearn-estimator — ограниченный allowlist из `get_params()`. Существующий metadata в run содержал только class chain и не позволял увидеть применённые defaults.
4. После компактизации сохранять в сообщении измеренные baseline-параметры и статистику дисбаланса. В первом classification request полный profile содержал частоты классов, но последующие requests заменяли `data_profile` строкой первых 2 000 символов, где их уже не было. Manifest `build_model` при этом содержал только список классов, без частот и y.
5. Передавать последнюю ошибку только пока она остаётся последним результатом либо маркировать её как историческую. Сейчас `prompts.py:37` выбирает последний неуспешный trial даже после более позднего успешного; например, requests для `trial_0006`—`trial_0008` всё ещё содержали код упавшего `trial_0004`. Сохранять текущий ledger и устаревшую ошибку раздельно.
6. Выдавать «ранняя остановка включена» только если host реально передаёт допустимый validation `eval_set` и записывает остановленную итерацию; иначе параметр исключать из recipe и контекста.
7. Сохранить defaults успешного baseline при наследовании recipe: в этом запуске явный LR .05/.03/.02 заменял измеренный автоматический .48828. Новую гипотезу сравнивать с предыдущей успешной recipe и не тратить trial на идентичный fingerprint.
8. В отчёте отдельно показывать validation F1 и recall по классам для задач с Macro F1. Это быстро выявило бы, что «веса» отсутствуют, а recall редких классов провалился.

Индикаторы пропусков regression можно строить проверенным `SimpleImputer(add_indicator=True)`, который добавляет индикаторы к результату импутации. [Документация `SimpleImputer` для scikit-learn 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.impute.SimpleImputer.html). Это заменяет хрупкую ручную передачу DataFrame через вложенные lambda-преобразователи; сами предыдущие trials не проверяли качество такого варианта.
